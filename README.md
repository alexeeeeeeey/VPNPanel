# VPNPanel

VPNPanel — децентрализованная панель управления конфигурациями Xray. Узлы работают без центрального сервера: у каждого своя база SQLite, изменения синхронизируются между подключёнными панелями. Пользователями и общей библиотекой конфигов можно управлять с любого узла. При потере связи узел продолжает работать со своими данными, а после восстановления связи обменивается изменениями с остальными.

У каждого пользователя два отдельных UUID: MAIN для безлимитного доступа и LIMITED для доступа с месячным лимитом трафика. Лимит LIMITED общий для всех узлов; его исчерпание не отключает MAIN. Срок действия и блокировка пользователя распространяются на оба UUID.

Панель поддерживает JSON-шаблоны, подписки Happ и учёт трафика. Серверная часть написана на Go, интерфейс — на Vue 3 и TypeScript.

## Установка

На Linux с systemd выполните от root:

```sh
bash <(curl -fsSL https://github.com/alexeeeeeeey/VPNPanel/releases/latest/download/install.sh)
```

Если вход выполнен обычным пользователем:

```sh
curl -fsSL https://github.com/alexeeeeeeey/VPNPanel/releases/latest/download/install.sh | sudo bash
```

Установщик поддерживает amd64 и arm64. Скачивает последний стабильный релиз панели и CLI, проверяет SHA-256 и версию, создаёт пользователя `vpnpanel` и запускает службу systemd. Для запуска не нужны Go, Node.js и отдельная сборка интерфейса. На Debian/Ubuntu и системах с dnf/yum недостающие зависимости устанавливаются автоматически.

Бинарники находятся в `/opt/vpnpanel`, база — в `/var/lib/vpnpanel`, ключи — в `/etc/vpnpanel`. Повторный запуск устанавливает актуальный релиз, сохраняет базу, ключи и существующий файл службы. Служба перезапускается; управляемый ею Xray также будет остановлен на время перезапуска.

Панель слушает `127.0.0.1:9080`, путь `/panel`. После установки настройте nginx и клиентский сертификат по разделу «Доступ к панели». Xray устанавливается отдельно; его параметры добавляются в `ExecStart` службы через `systemctl edit --full vpnpanel`. Установщик не меняет существующую конфигурацию nginx.

Состояние и журнал:

```sh
systemctl status vpnpanel
journalctl -u vpnpanel -f
```

Команда установки станет доступна после публикации первого релиза.

## Сборка из исходников

Для сборки нужны Go 1.26 или новее и Node.js с npm. Для доступа к панели нужен nginx с проверкой клиентского сертификата. Для управления VPN и учёта трафика нужен Xray.

Из корня проекта:

```sh
npm --prefix frontend install
npm --prefix frontend run build
go build -o dist/vpnpanel ./cmd/vpnpanel
go build -o dist/vpnpanelctl ./cmd/vpnpanelctl
```

На Windows для бинарников можно указать имена `dist/vpnpanel.exe` и `dist/vpnpanelctl.exe`.

Frontend встраивается в бинарник панели через `go:embed`. Сначала нужно собрать интерфейс, затем Go-бинарник. Для запуска готовой панели Node.js и каталог `frontend/dist` не требуются. После изменения интерфейса нужно повторить обе сборки.

Пример запуска на Linux после настройки доступа:

```sh
export VPNPANEL_MTLS_PROXY_KEY_FILE=/etc/vpnpanel/access/proxy.key
export VPNPANEL_NODE_KEY=YOUR_NODE_API_KEY

./dist/vpnpanel \
  -listen 127.0.0.1:9080 \
  -db data/panel.db \
  -base-path /panel \
  -xray /usr/local/bin/xray \
  -xray-api 127.0.0.1:10085
```

Ключ узлового API можно создать командой `openssl rand -hex 32`. Сохраните его в окружении службы и используйте при последующих запусках. При смене ключа потребуется обновить подключения на других панелях.

Параметры запуска:

- `-listen` — адрес backend, по умолчанию 127.0.0.1:9080. Допускаются только loopback IP.
- `-db` — путь к SQLite, по умолчанию data/panel.db.
- `-web` — внешний каталог собранного frontend. Если флаг не задан, используются файлы, встроенные в бинарник.
- `-base-path` — префикс URL панели. Если флаг не задан, используется VPNPANEL_BASE_PATH.
- `-xray` — путь к бинарнику Xray. Без флага панель не управляет процессом.
- `-xray-api` — loopback-адрес API статистики Xray.
- `-connection-url` — вывести строку подключения узла и завершиться.
- `-node-name` — задать имя своего узла.
- `-version` — вывести версию бинарника и завершиться.

Без `-xray` доступны библиотека, сборка JSON, подписки и обмен данными. Применение конфигурации к внешнему Xray в этом режиме выполняется отдельно.

При сборке из исходников службу панели нужно настроить самостоятельно. Отдельная служба Xray не должна занимать порты управляемого процесса.

## Доступ к панели

Панель открывается через nginx по HTTPS с клиентским сертификатом. Backend слушает локальный адрес и принимает подтверждение сертификата только от доверенного прокси.

Парольного входа нет. Прямое обращение к backend без доверенных заголовков возвращает 404. Одна лишь сборка и запуск backend не открывают панель в браузере.

Клиентский сертификат используется для входа из браузера. Ключ прокси подтверждает обращения nginx к backend. Отдельный `VPNPANEL_NODE_KEY` используется для связи между панелями через `/node-api/`.

Ключ прокси — 64 шестнадцатеричных символа, например результат `openssl rand -hex 32`. Файл читается через `VPNPANEL_MTLS_PROXY_KEY_FILE`; альтернативно ключ можно передать в `VPNPANEL_MTLS_PROXY_KEY`. Одновременно оба источника не используются. Ключ узлового API — 32–256 символов без пробелов и переводов строк.

Для браузера нужен клиентский сертификат от своего CA с назначением `clientAuth`, установленный вместе с закрытым ключом, обычно через PKCS#12 (`.p12`). Серверный TLS-сертификат домена — отдельный, например от Let's Encrypt. Один клиентский сертификат работает на всех узлах, доверяющих этому CA. Отдельные сертификаты устройств позволяют отзывать их независимо.

Пример серверного блока для `/panel`. Пути и значение `X-Panel-Proxy-Key` заменяются своими; значение заголовка должно совпадать с содержимым `proxy.key` у backend.

```nginx
server {
    listen 443 ssl;
    server_name panel.example.com;

    ssl_certificate     /etc/letsencrypt/live/panel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/panel.example.com/privkey.pem;
    ssl_client_certificate /etc/vpnpanel/trust/ca.crt.pem;
    ssl_crl                /etc/vpnpanel/trust/ca.crl.pem;
    ssl_verify_client optional;
    ssl_session_cache off;
    ssl_session_tickets off;

    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Panel-Client-Verify $ssl_client_verify;
    proxy_set_header X-Panel-Proxy-Key REPLACE_WITH_64_HEX_CHARACTERS;
    proxy_set_header X-Panel-CLI "";

    location = /panel {
        if ($ssl_client_verify != SUCCESS) { return 404; }
        return 308 /panel/;
    }

    location ^~ /panel/node-api/ {
        proxy_pass http://127.0.0.1:9080;
    }

    location /panel/ {
        if ($ssl_client_verify != SUCCESS) { return 404; }
        proxy_pass http://127.0.0.1:9080;
    }

    location / { return 404; }
}
```

`ssl_verify_client optional` оставляет межузловой API доступным без браузерного сертификата. Его защищает `VPNPANEL_NODE_KEY` на backend. Остальные пути панели требуют успешной проверки сертификата. Служебные заголовки перезаписываются nginx, признак CLI очищается.

Закрытый ключ CA остаётся у владельца. Узлам достаточно публичных CA и CRL. Ключ прокси и конфиги с его значением доступны только пользователю службы и nginx.

При отзыве сертификата новый CRL нужно доставить на каждый узел, затем проверить конфиг и перезагрузить nginx. Панель не реплицирует сертификаты и CRL. У списка отзыва есть срок действия: обновление требуется и без новых отзывов. При экстренном отзыве уже открытые соединения завершаются отдельно.

Кнопка «Выйти» устанавливает cookie выхода. Она не отзывает сертификат: владелец может войти повторно или открыть другой профиль браузера.

## Пользователи

При создании пользователя выдаются два UUID. MAIN используется для основного доступа без отдельного лимита трафика. LIMITED используется для доступа с месячной квотой, общей для всех узлов.

UUID создаются вместе с пользователем и сохраняются при изменении конфигов. Каждую учётку можно перевыпустить отдельно. Отключение пользователя и истечение срока убирают обе учётки из следующей серверной сборки и закрывают выдачу подписки.

`limited_bytes = 0` означает отсутствие лимита. Квота считается за календарный месяц по Europe/Moscow, а не за 30 дней с даты создания. В новом месяце доступный объём восстанавливается; пожизненный расход остаётся.

Для LIMITED нужен отдельный inbound со своим списком клиентов. Если в этот inbound добавить MAIN, пользователь сможет подключаться через него без учёта квоты LIMITED.

Срок доступа задаётся точно или продлевается на месяц/квартал. Продление прибавляет календарные месяцы к действующему сроку; если срока нет или он истёк, отсчёт начинается с текущего времени.

## Шаблоны и переменные

Откройте раздел «Конфиги» и создайте серверный или клиентский шаблон. Шаблоны хранятся в общей библиотеке. В настройках узла задайте переменные и выберите серверный шаблон для применения.

```jsonc
{
  "inbounds": [
    {
      "tag": "main",
      "listen": "$LISTEN_IP",
      "port": $PORT,
      "protocol": "vless",
      "settings": { "clients": $CLIENTS_MAIN, "decryption": "none" }
    },
    {
      "tag": "limited",
      "listen": "$LISTEN_IP",
      "port": $LIMITED_PORT,
      "protocol": "vless",
      "settings": { "clients": $CLIENTS_LIMITED, "decryption": "none" }
    }
  ],
  "outbounds": [{ "protocol": "freedom", "tag": "direct" }]
}
```

Это шаблон: валидным JSON он становится после подстановки. Например, `LISTEN_IP = 127.0.0.1`, `PORT = 10001`, `LIMITED_PORT = 10002`.

Доступные системные переменные:

- `$USER_UUID` или `$UUID` — MAIN UUID выбранного пользователя.
- `$USER_UUID_LIMITED` или `$UUID_LIMITED` — LIMITED UUID выбранного пользователя.
- `$CLIENTS_MAIN` — массив MAIN-учёток активных пользователей.
- `$CLIENTS_LIMITED` — массив LIMITED-учёток с доступной квотой.

Остальные переменные, например `$HOST` и `$PORT`, задаются в настройках узла.

Имена переменных — латинские `A–Z`, цифры и `_`, первый символ — буква. Обязательные переменные из шаблона появляются в редакторе настроек узла.

`$` работает как текстовая подстановка, в том числе внутри строк. Кавычки, запятые и JSON-структура задаются шаблоном. Значения с кавычками или обратными слешами требуют корректного JSON-экранирования.

Старый синтаксис `"&UUID"`, `"&UUID_LIMITED"`, `"&CLIENTS_MAIN"`, `"&CLIENTS_LIMITED"` тоже поддерживается. Метка с `&` занимает целое строковое значение и заменяется значением с сохранением типа. Для пользовательских переменных это работает так же: числовой `PORT`, переданный через API, даст число; текст из поля интерфейса останется строкой. Для порта в UI удобнее запись `"port": $PORT`.

Списки клиентов содержат `id` и стабильный `email`: `<user-id>.main` или `<user-id>.limited`. По этим email собирается трафик. Дополнительные поля клиентов, например `flow`, системные списки сейчас не добавляют.

### Клиентские шаблоны

Клиентские шаблоны не выводятся из серверных. Они могут вести на CDN, внешний балансировщик или сервер, которого нет в списке панелей. Наличие узла в интерфейсе не проверяет работоспособность адреса из клиентского JSON.

```jsonc
{
  "outbounds": [{
    "tag": "main",
    "protocol": "vless",
    "settings": {
      "vnext": [{
        "address": "$HOST",
        "port": $PORT,
        "users": [{ "id": "$USER_UUID", "encryption": "none" }]
      }]
    }
  }]
}
```

Транспорт, TLS и маршрутизация добавляются под конкретную схему подключения. Всё, что подставляется в клиентский шаблон, доступно владельцу подписки.

## Управление Xray

Узел раз в 4 секунды собирает назначенный серверный шаблон. Если результат изменился, панель проверяет его через `xray run -test -config`, затем перезапускает управляемый процесс.

Если актуальный конфиг не собирается или не проходит проверку, работающий Xray останавливается. Отката к старому конфигу нет: иначе отозванные UUID и исчерпанные квоты могли бы продолжать работать. После исправления панель повторяет запуск автоматически.

Перезапуск закрывает текущие соединения, в том числе MAIN при исчерпании квоты LIMITED. Проверка JSON и проверка ядром не подтверждают доступность доменов, CDN и транспортов снаружи.

На Linux управляемый Xray завершается вместе с панелью, включая аварийный `SIGKILL`. После запуска панель восстанавливает конфигурацию из базы. За перезапуск самой панели отвечает менеджер служб.

## Подписки Happ

В разделе «Подписки» включите выдачу, укажите IP, порт и путь. Начальные настройки — `127.0.0.1:9090`, путь `/sub`. В интерфейсе задаются внешний URL, название, описание, ссылки поддержки и сайта, интервал обновления.

Выберите пользователя и скопируйте его ссылку в Happ: `https://vpn.example.com/sub/<sub_id>`. Ответ — JSON-массив клиентских конфигов с заголовками профиля Happ. Для внешнего доступа слушатель публикуется через HTTPS-прокси отдельно от административного mTLS-доступа.

Подписка перебирает клиентские шаблоны и сохранённые наборы переменных узлов. Варианты с незаполненными переменными пропускаются, одинаковые результаты не дублируются. Новые шаблоны появляются при следующем обновлении подписки клиентом.

Удаление подключения к панели не чистит сохранённые переменные и не удаляет соответствующие варианты из подписки. Клиентские шаблоны могут содержать любые адреса независимо от подключений к панелям.

Для переноса из 3x-ui можно сохранить прежний `subId` в поле Sub ID. Полная ссылка сохранится при том же внешнем домене и пути. Изменение Sub ID заменяет ссылку, но не перевыпускает UUID.

Ссылка подписки даёт доступ к учётным данным. Закрытие выдачи подписки само по себе не стирает уже загруженный JSON из клиента; доступ прекращается после применения актуального списка пользователей на сервере.

## Подключение узлов

В разделе «Серверы» добавьте узел по имени, URL и API-ключу либо вставьте строку подключения. HTTPS обязателен для удалённых адресов; HTTP разрешён для loopback, например через SSH-туннель.

Строка подключения создаётся на узле с его базой и тем же окружением, с которым работает служба:

```sh
./dist/vpnpanel \
  -db data/panel.db \
  -base-path /panel \
  -node-name nl-1 \
  -connection-url https://nl.example.com/panel
```

Строка содержит UUID узла, имя, URL и API-ключ в Base64. Она не зашифрована и должна храниться как секрет.

Обмен идёт каждые 4 секунды, без выделенного главного узла.

Пользователи, UUID, сроки, лимиты, библиотека конфигов и состав сети синхронизируются между панелями. Переменные и назначение серверного конфига копируются с привязкой к UUID владельца и применяются только на его узле. Статистика трафика, IP и устройств объединяется.

Настройки слушателя подписок, метаданные профиля, сертификаты, ключ прокси и системные метрики остаются локальными.

При потере связи изменения остаются в локальной базе. После восстановления побеждает версия записи с большей меткой времени; при равенстве — с большим UUID источника. Поэтому часы узлов должны быть синхронизированы. Одновременное редактирование разных полей одного пользователя не объединяется: побеждает запись целиком.

Журнал передаётся полностью с пределом 2 МиБ на пакет. Инкрементальной передачи и разбиения на страницы пока нет; при превышении предела синхронизация перестанет проходить. Конфликт одинаковых Sub ID у разных пользователей также отклоняет пакет.

Журнал содержит пользовательские UUID и API-ключи подключений. Все подключённые панели считаются доверенными.

## Статистика

Для сбора нужны `-xray-api` и статистика в серверном конфиге Xray:

```json
{
  "stats": {},
  "api": {
    "listen": "127.0.0.1:10085",
    "services": ["StatsService"]
  },
  "policy": {
    "levels": {
      "0": {
        "statsUserUplink": true,
        "statsUserDownlink": true,
        "statsUserOnline": true
      }
    }
  }
}
```

Этот фрагмент добавляется в полноценный серверный шаблон. Учёт использует email из `$CLIENTS_MAIN` и `$CLIENTS_LIMITED`.

Сборщик раз в 15 секунд читает и сбрасывает счётчики Xray, затем записывает дельты в SQLite. Не используйте одновременно другой сборщик, который сбрасывает те же счётчики: часть расхода не попадёт в панель. При аварии между сбросом и записью последняя дельта может потеряться.

Повторная доставка снимка между узлами не удваивает расход: счётчики объединяются по максимумам. Квота применяется с задержкой опроса, доставки и перезапуска; при разделении сети расход других узлов временно неизвестен. Возможен расход сверх квоты в пределах этой задержки.

- `total_main`, `total_limited` — пожизненный расход по всем узлам.
- `quota_limited` — LIMITED за текущий месяц по Москве.
- IP — наблюдения из `statsonlineiplist -all`; короткое подключение между опросами может не попасть в список.
- Устройства — сведения из запросов подписки, а не список активных VPN-соединений.

HWID берётся из `X-HWID`, `X-Device-ID` или `X-Client-HWID`. Дополнительно сохраняются User-Agent, ОС, модель, версия приложения, локаль, IP и время обращения. Без HWID записи группируются по User-Agent. Эти значения сообщает клиент: новый HWID создаёт новую запись, а число записей не равно гарантированному числу физических устройств.

Прокси подписок может передавать `X-Real-IP`; backend учитывает его только для соединений от loopback. Без прокси используется адрес TCP-соединения.

Системные графики обновляются раз в 4 секунды, история за последние 5 минут хранится в памяти. Перезапуск панели очищает эту историю. Статус «В сети» означает доступность API панели, а не успешное подключение к VPN.

## Командная строка

`vpnpanelctl` использует алиасы из `~/.ssh/config`, включая `User`, `Port`, ключи и `ProxyJump`. На узле нужны запущенная панель и `curl` с `--fail-with-body`. SSH работает в `BatchMode`, без интерактивного ввода пароля.

Локальный файл `/etc/vpnpanel/access/cli.headers` на сервере содержит:

```text
X-Panel-Proxy-Key: REPLACE_WITH_64_HEX_CHARACTERS
X-Panel-CLI: 1
```

Ключ совпадает с ключом прокси backend. Файл читается удалённым `curl` через SSH и доступен только доверенному пользователю (`0600`). Клиентский закрытый ключ браузера для CLI не нужен.

```sh
vpnpanelctl -host nl-1 -base-path /panel -auth-file /etc/vpnpanel/access/cli.headers state
vpnpanelctl -host nl-1 -base-path /panel -auth-file /etc/vpnpanel/access/cli.headers user-add 'Петя'
vpnpanelctl -host nl-1 -base-path /panel -auth-file /etc/vpnpanel/access/cli.headers user-disable USER_ID
vpnpanelctl -host nl-1 -base-path /panel -auth-file /etc/vpnpanel/access/cli.headers user-enable USER_ID
vpnpanelctl -host nl-1 -base-path /panel -auth-file /etc/vpnpanel/access/cli.headers template-save server 'Основной' ./server.json
vpnpanelctl -host nl-1 -base-path /panel -auth-file /etc/vpnpanel/access/cli.headers render client ./client.json USER_ID
```

`USER_ID` — внутренний `id` пользователя из `state`, не UUID подключения и не Sub ID. Вместо файла шаблона можно передать `-` и читать stdin. Ответы — JSON, ошибка даёт ненулевой код выхода. `-port` задаёт порт backend на удалённом узле; SSH-порт берётся из OpenSSH-конфига.

## Обслуживание

SQLite хранит пользователей, шаблоны, настройки, статистику и журнал репликации. Каталог `data/` содержит секреты и исключён из Git, как и результаты сборки.

Для резервной копии работающей базы используется SQLite backup API или команда `.backup` в SQLite CLI. Простое копирование одного `panel.db` во время работы может пропустить данные из WAL. Альтернатива — корректно остановить панель перед копированием.

## Обновление панели

Панель получает обновления из релизов https://github.com/alexeeeeeeey/VPNPanel. Адрес задан в коде; переменная `VPNPANEL_RELEASE_REPO` больше не используется. Пока репозиторий или первый релиз не опубликованы, проверка сообщает об отсутствии релизов.

Релизные сборки на Linux проверяют обновления при запуске и затем каждые шесть часов. Если опубликована новая стабильная версия, панель скачивает бинарник для своей архитектуры, проверяет SHA-256 по файлу `SHA256SUMS` и запускает его с `-version` для проверки. После успешной проверки бинарник заменяется атомарно, панель останавливает рабочие процессы и перезапускает себя с прежними аргументами и окружением. Frontend обновляется вместе с бинарником. База и настройки остаются на месте. Управляемый Xray также перезапускается, поэтому текущие VPN-соединения будут закрыты.

На главной странице есть кнопка проверки и, при наличии новой версии, кнопка установки. Они относятся к выбранному узлу. После обновления локального узла страница перезагружается автоматически. При ошибке загрузки, контрольной суммы или проверки версии работающий бинарник не заменяется.

Каталог бинарника должен быть доступен пользователю службы для записи. Для установки под отдельным пользователем подходит `/opt/vpnpanel`, а не общий `/usr/local/bin`:

```sh
install -d -o vpnpanel -g vpnpanel -m 755 /opt/vpnpanel
install -o vpnpanel -g vpnpanel -m 755 vpnpanel-linux-amd64 /opt/vpnpanel/vpnpanel
```

В systemd путь `ExecStart` должен указывать на `/opt/vpnpanel/vpnpanel`. При использовании `ReadOnlyPaths`, `ProtectSystem` и других ограничений службы запись в этот каталог должна быть разрешена. Давать панели право записи во весь `/usr/local/bin` не требуется.

Автоматическая установка поддерживается на Linux amd64 и arm64. Windows-сборки публикуются для ручной замены. Локальные версии с суффиксом `-dev` не устанавливают обновления автоматически; ручная проверка и установка на Linux остаются доступны. Предварительные версии и понижение версии не устанавливаются.

## Публикация релиза

Workflow `.github/workflows/build.yml` запускается при push и pull request: собирает frontend, выполняет Go-тесты, `go vet` и сборку на Linux и Windows. На Linux дополнительно выполняются тесты с детектором гонок.

Для выпуска создайте и отправьте тег вида `v1.0.0`:

```sh
git tag v1.0.0
git push origin v1.0.0
```

После успешных проверок workflow собирает панель со встроенным frontend и CLI для Linux и Windows, архитектуры amd64 и arm64. Версия из тега записывается в бинарники. Вместе с файлами публикуется `SHA256SUMS`. Релиз сначала создаётся как черновик и становится доступным для обновления после загрузки всех файлов.

Публикация использует стандартный `GITHUB_TOKEN` с правом `contents: write` в job релиза. Отдельный токен в настройках панелей не нужен; репозиторий и релизы должны быть публичными.

## Разработка

```sh
go test ./...
npm --prefix frontend run build
```

`npm --prefix frontend run dev` запускает Vite на loopback. Его `/api` проксируется в `127.0.0.1:9080`, но это не отменяет проверку доступа backend: стандартный Vite-прокси сам по себе mTLS-авторизацию не настраивает.

Код запуска находится в `cmd/vpnpanel/main.go` и `cmd/vpnpanelctl/main.go`. Обработчики HTTP, доступ, работа с Xray, подписки, синхронизация узлов и хранение данных разделены по пакетам в `internal`. Интерфейс находится в `frontend`.
